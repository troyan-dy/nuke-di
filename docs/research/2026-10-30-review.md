# 3.0 review, 2026-10-30

What to cut, what to fix and what to add before nuke-di 3.0. The ranked backlog is the epic #89; this page keeps
the evidence and the reasoning behind it.

Method: five parallel research passes over 2.0.1 (`8faacd2`): the core and public API, the framework integrations
and the maintenance surface, competitors and their users' demand, a verdict on every open issue, and adoption
(first impression, positioning, findability). An independent review then checked the merged list against the
code; its corrections are applied below. Settled before the research: the library has no users, so 3.0 breaks
whatever it needs without deprecations; `NotSingletonClient` goes and `Client` becomes the base class; the
rejected designs (ADR-0005, 0006, 0008, 0009, 0010) stay rejected.

## Diagnosis

Nobody uses nuke-di because nobody has been told it exists. In the 14 days before the review the repository had
15 unique visitors, all referrers were GitHub and Google, the only star is the author's, and the PyPI downloads
are CI and mirrors (3,938 of 4,680 with no system, 526 Linux runners, 216 the author's Mac). A web or GitHub
search for "nuke-di" does not find the project: "nuke python" is Foundry Nuke, `nuke` on PyPI deletes
directories, and GitHub returns Discord "nuker" bots. One of five awesome-list pull requests was merged.

The 43 releases went to breadth: eight framework integrations, a mypy plugin, comparison benchmarks, an agent
skill and its paid eval. The integrations and their kit are 42 % of `src/`, 41 % of the tests and two thirds of
the guide, and the rules for agents are restated in eight places.

The core is in good shape: 100 % branch coverage, strict mypy, free-threaded CI, and the review found one real
bug (#128). What competitors' users ask for most, and wait years for, is what nuke-di already does: concurrent
startup (dishka #45, open since 2024), app-scoped singletons in FastAPI (FastAPI discussions #8054, #16478),
teardown that survives a failure or a cancellation (that-depends #272, wireup #141, dependency-injector
#968/#941), thread safety without the GIL (dependency-injector #905). None of that is on the README's first
screen, which competes on "simplest" instead.

The proposal is therefore: shrink to the model, fix the core, then launch with a positioning that says what
nuke-di is instead of. The counter-position, argued by the review, is to launch on 2.x first and cut only after
seeing which integrations draw people: integration breadth is how competitors compete, the outreach channels
include the aiogram, FastStream and Litestar communities, and the integrations have cost little so far (their
tests run in 1 s and nothing has broken). That choice is #123.

## Core and public API

- #128: a `BaseException` from a client's `connect()`, the library's own `ConnectError` included, leaves the
  container connected and the clients that did connect are never disconnected. Small fix; can ship as 2.0.2.
- #131: `ConnectError` and `InitializeDependencyError` are `SystemExit`, which costs a wrapper, a translation in
  every integration and a contract check, and turns a wrong call order in a test into a `SystemExit`. With #44
  (exit codes, #50 folded in) it settles what a failed process reports.
- #129, then #130: with every client a singleton the container keeps one registry by class instead of two lists
  and four `id()`-keyed dicts, and the graph loses its instance numbering.
- Cuts: #132 `client_dataclass` (identical to `@dataclass` on a `Client` subclass), #133 `CONNECT_CONCURRENCY`
  (a leftover of the layered scheduler), #134 the 1.x shims and small inconsistencies.
- Container API: #58 (typed access through `resolve()` in any state, identity equality, `repr`, settings-only
  constructor) and #61 (read the global container's settings at first connect).
- Silent traps a newcomer hits in the first ten minutes: #135 (`inject()` accepts an optional or positional-only
  client and a plain class parameter that `__init__` refuses) and #137 (an injected function runs against a
  container that is not connected, or was flushed, without a word).
- #136: `async with DI` never sets `Shutdown` and stops `BackgroundTasks` in reverse-dependency order, while
  `running()` does both first. It matters once framework recipes use `async with DI`.

## Integrations and the maintenance surface

Every framework but FastAPI has its own documented way to hand a handler an object (`workflow_data`,
`TaskiqDepends(fn)`, `Provide`, a server lifespan with `Context`, `app.state`). The modules exist to remove one
marker per handler, and most of the pitfalls they handle come from rewriting signatures: private attributes of
eight libraries, cached signatures, reserved names. Each module can become a 6–15 line recipe on one guide page,
run as a tested guide block: #140 aiogram, #141 taskiq, #142 MCP SDK, #143 FastMCP, #144 Litestar,
#145 FastStream, #146 ASGI. FastAPI stays and gets simpler (#138); the kit becomes private (#139); the remaining
framework floors move to their current majors and the seven `*-min` CI jobs go (#147). Closing any of these
keeps that module.

Around the library: #154 removes the paid agent eval that ran once; #155 removes the implemented specs, the
ralphex plan artefact and the stock ralphex prompts; #156 replaces "update eight places by hand" with one source
and a drift test; #153 makes the guide the single runnable source and keeps the eight application examples,
after #63 runs the guide's blocks; #157 takes the 29-second benchmark run out of the default test run.

## Competitors

Three tiers: legacy giants (dependency-injector 8.3 M downloads a month, injector, svcs), the 2024 generation
with providers, scopes and many integrations (dishka 844 K, wireup 122 K, that-depends 44 K, anydi, aioinject),
and FastAPI `Depends` as the default nobody chose. All of them compete on integration count, validation and
speed; none owns the startup and shutdown of a process.

Most asked across their trackers, and what nuke-di does about it:

- "How is this different, how do I migrate": #150, a page for dishka, wireup, dependency-injector and `Depends`
  users with a concept map (and #87, a runtime bridge to dishka, recommended to close in its favour).
- "What happens when startup or shutdown fails": #148, one table of guarantees, each row linked to its test.
- Scopes, Protocol binding, configuration providers, health pings: rejected or recipes here, so #151 puts the
  recipes and the reasons on one page instead of only in ADRs.
- Typing edge cases (PEP 695 aliases, `NewType`, `ty`): #158.
- A test that receives a client by type hint (dishka #124, open since 2024): #163, later.

Confirmed by demand and still rejected: per-request scopes (dependency-injector #728, 52 comments), Protocol
binding (dependency-injector #823, its most-reacted open issue), provider functions, retries, a compiled core.

## Positioning and launch

- #149: the README's first screen says what nuke-di is instead of: the startup and shutdown of an async process,
  a when-to-pick-what table (dishka for scopes, `Depends` for per-request, svcs for a locator), and "not for you
  if". The startup figure is "against dishka and wireup"; dependency-injector starts as fast.
- #152: a documentation site; every competitor with traction has one. #159: `__version__` and `python -m nuke_di`.
- After 3.0: #160 a written versioning policy and the `4 - Beta` classifier (43 releases in three weeks and a
  2.0 made of renames read as churn); #161 the repository front (description, social preview, Discussions,
  SECURITY.md, CONTRIBUTING.md); #162 one post in English and on Habr around the startup figure, three threads
  (r/Python, Show HN, FastAPI Discussions) and a follow-up on the open awesome-list pull requests.

## Corrections from the review

- GitHub Releases exist for all 43 tags (`release.yml`); the adoption pass checked a tag without the `v`.
- `async with DI` does stop background tasks (`BackgroundTasks.disconnect()` calls `stop()`); the gap is
  `Shutdown` and the order (#136).
- `loop_factory` (#49) is not urgent: the library does not use the event loop policy API.
- The "ten times faster startup" holds against dishka and wireup only.
